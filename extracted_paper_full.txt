This paper presents EdgeSync, a distributed edge computing framework that divides the city into regional clusters and deploys localized microservices for ETA computation. Each cluster includes services for rider distance, restaurant preparation, traffic analysis, and ETA aggregation, while a gossip-based protocol enables decentralized synchronization between regions. The ETA model combines pickup time, preparation time, delivery distance using the Haversine formula, and traffic conditions. Experimental results show reduced latency, improved fault tolerance, and better scalability compared to centralized approaches, making EdgeSync an effective solution for urban delivery ecosystems.Keywords - Edge computing, ETA prediction, distributed systems, gossip protocol, food delivery, microservices, real-time systems, Mumbai, Haversine distanceIntroduction The rapid expansion of food delivery services, like Zomato and Swiggy in major metropolitan areas in India, presents a unique challenge with respect to accurately estimating the amount of time it will take to get food from the restaurant to the end-user (ETA). Inaccuracies in ETA predictions have direct effects on customer satisfaction, order cancellations, and operational efficiency [1].Mumbai, with its severe traffic congestion due to the monsoon season (traffic may vary by as much as 60% over a one-hour period due to the monsoon season), is home to over 20 million people living in multiple, geographically separated neighbourhoods [2] [3], presents perhaps the greatest challenge to predicting delivery times and routing, as well as computing ETAs. Traditional methods for routing ETAs through a single instance of cloud computing are unable to accommodate the variability present in real time within these delivery environments.This study develops a distributed edge computing framework named EdgeSync that was developed to solve these problems. EdgeSync creates three geographically-defined edge clusters (East, West, and Central) in Mumbai, and within each of these clusters deploys independent microservices to perform local computations on the proximate distance to the rider, the current state of restaurant preparation, the level of congestion that the rider is likely to encounter along the way, and the aggregate ETA state between edges through a gossip-based synchronization protocol. This architecture allows for significant increases in the efficiency of delivering food in Mumbai by using less time, money, and resources than previously possible through cloud computing approaches.Below is a list of the main contributions of this paper: (1) A regionally-aware ETA microservice architecture (for example, an edge deployed ETA Microservice Architecture); (2) A Haversine-based distance and time speed model for estimating the real travel time to the specified destination; (3) An implementation of a gossip protocol; and (4) An interactive click-based simulation interface built with Streamlit to allow for realtime ETA breakdowns based on user-selected origins/destinations.The remainder of this manuscript is organized in the following manner: section II provides background for prior research; section III outlines the system architecture; section IV describes the methodology used to compute ETA; section V includes a description of the gossip protocol and how it synchronizes states; section VI gives a description of the experimental evaluation completed; section VII includes a discussion of our findings; and finally, section VIII will provide closure to this article.Related WorkMachine Learning for Food Delivery ETAFood delivery time prediction research in Indian cities suggest that ensemble models with gradient boosting variants like LightGBM, which combine real-time data about traffic, weather, and geospatial distance, create very accurate predictions [3]. This demonstrates that the use of dynamic and local information features is much more effective than static historical averages as inputs for predictive models [3], [4].Edge Computing for Real-Time Decision MakingResearch on smart transportation shows that moving computations closer to data sources through the use of edge nodes allows for much lower latency than using centralized cloud-based computing for real-time decision making [5], [6]. Additionally, the use of a distributed architecture that preprocesses sensor data at the edge of the network and only sends relevant summaries to the cloud is able to decrease end-to-end decision latency by 60—95% in IoT-intensive deployments [6].Gossip Protocols in Distributed SystemsGossip-based communication protocols have been shown to be scalable and fault-tolerant methods for disseminating information in distributed and IoT environments. Their epidemic propagation model will ensure eventual consistency without requiring any individual node to keep a global state, which makes them ideal for use in dynamic urban sensor networks and smart city applications [7]. Moreover, because gossip protocols are decentralized, nodes will continue to operate and synchronize in the event of partial network failures [9]-[11].Positioning of EdgeSyncThe EdgeSync architecture integrates three major components to form a single city-scale delivery prediction system that uses machine learning models, edge computing for data processing and telemetry, and lightweight algorithms for gossip synchronization. It does this by using region-aware partitioning of geographic areas based on the location of delivery origins or destinations. This enables synchronization between clusters via a REST API while managing latency, fault tolerance, and scalability challenges associated with traditional centralized systems.This section builds on sections I and II and correlates key research threads identified during the literature survey in section II with design decisions made during the development of EdgeSync. First, there is strong evidence that live, real-time, & dynamic delivery prediction variables (=live traffic levels, variability in preparation time (i.e., stochastic), and real-time proximity to riders) provide better estimates than static average delivery time history. Therefore, EdgeSync leverages live traffic levels, stochastic preparation times, and real-time rider proximity to provide delivery estimations.Second, edge deployments consistently deliver lower latency to users (i.e., faster time to receive responses for end users) compared to centralized clouds within highly latency-sensitive urban edge environments. Thus, bringing computation closer to the data creates the best architecture for this solution.Third, a major advantage of gossip-based protocols is their proven ability to operate successfully within IoT-based and smart-city type architectures. Gossip is the preferred method of synchronizing systems that require coordination between multiple components when centralized coordination is not feasible or practicable.One significant finding from the literature reviewed is the conspicuous absence of any successful architectural implementation that combines ML-informed ETA predictions, regional microservices deployed at the edge, and gossip-based synchronization into one cohesive framework. EdgeSync solves this problem by creating an architecture that supports the integration of any sufficiently accurate prediction model (e.g., machine learning based) in a distributed, regionally-sensitive, fault-tolerant manner. EdgeSync does not provide a new machine learning model; rather, it provides an architectural framework to be used by any portable enough prediction model to allow for that model to be deployed successfully as part of the EdgeSync delivery experience.According to [3] and [4], EdgeSync is the better design option than hybrid edge and cloud approaches, as it eliminates the need for cloud resources to run any ETA calculations. In EdgeSync, the cloud simply routes requests, or does stateless routing, which can be replaced easily, while predictions are made entirely at the Edge. This design is more resilient to the lack of cloud connectivity and has a lower median latency, in general, since source and destination are typically located in the same data center (not split between data centers).System ArchitectureFig. 1 illustrates the overall EdgeSync architecture. The system comprises three layers: a client-facing cloud coordination layer, three independent regional edge clusters, and a gossip synchronization ring connecting the clusters.Fig. 1. EdgeSync distributed system architecture with three regional edge clusters and gossip ring.Regional Edge Cluster DesignEdgeSync now has three edge clusters for Mumbai, India. Each cluster corresponds to a geographic area defined using the get_region function in config.py, which uses latitude/longitude for partitioning. The Central cluster contains all areas below 19.05°N, which includes the Islands and about three-fourths of Lower Parel. Activities occur within this region. The West cluster was created for locations in Mumbai west of 72.85°E, such as Bandra, Andheri West, and Malad. All other locations in Mumbai were placed into the East cluster (popularly Powai, Ghatkopar, and Vikhroli). Each cluster deploys their own independent FastAPI application, each on its own port. The East cluster is deployed on port 8000, West on port 9000, and Central on port 10000.Microservice Stack per ClusterEach regional node will expose two APIs. The /custom_eta API accepts a delivery request containing the source and destination coordinates, food type, proximity of the rider, and optional traffic conditions. The /custom_eta API processes everything required for the ETA computation pipeline. The /calc_delivery API processes a cross-region forwarding request. The /calc_delivery API returns only the delivery leg travel time between two regions, allowing cross-region delivery computation without exposing internal cluster states. Various /sync and /logs APIs also exist within each cluster to allow for exchange of gossip state and retrieval of logs, respectively. The APIs provide a level of abstraction whereby each microservice can be scaled, updated, or restarted independently of one another, thereby ensuring a stable and reliable overall system.Streamlit FrontendThe interactive user interface (UI) of the application was created using Streamlit framework Located in the file ui.py , it presents to users a clickable map of Mumbai. Users can choose a source location and a target location. After that they select which food item they would like to order from the map and how close of a distance the rider should be when they deliver the food item. The user can also provide an approximate traffic level as an option. The application then sends this request to the microservice that serves the source location and retrieves a structured ETA breakdown in response. The user interface presents the estimated pick up time, estimated preparation time, estimated delivery time, estimated traffic level and the total estimated ETA. The user may also see a list of all the live gossip synchronization logs in a sidebar panel of the User Interface.Fig. 2.  illustrates the interactive Streamlit-based frontend used in EdgeSync. It directs incoming delivery requests to the correct source-region microservice based on the source coordinates selected by the user and it is implementing the geographic partitioning approach that will be used in the edge nodes. The cloud coordination layer is stateless and will add almost no latency overhead.ETA Computation methodologyFig. 4 presents the complete ETA computation flowchart from request receipt to response. The process is fully deterministic given fixed inputs and a traffic level, with stochastic perturbation applied only to rider distance and preparation time sampling.Fig. 4. ETA computation flowchart for EdgeSync request processing.Distance EstimationEdgeSync uses the Haversine formula to compute the great-circle distance between two geographic coordinates, accounting for the curvature of the Earth. For two points (lat1, lon1) and (lat2, lon2), the distance d in kilometers is:	d = 2R · arctan2(√a, √(1−a))	where R = 6371 km is the Earth's radius and a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlon/2). This formula provides accurate distance estimates for intra-city distances in the range of 1–30 km.Traffic Speed ModelTravel time is estimated from distance and a traffic-level-dependent speed. Three discrete traffic levels are supported: Low traffic corresponds to 35 km/h, representing off-peak hours (before 08:00 and after 21:00); Medium traffic corresponds to 25 km/h for afternoon hours (12:00–16:00); and High traffic corresponds to 15 km/h for morning and evening peak hours (08:00–11:00 and 17:00–21:00). The dynamic_traffic function automatically selects the level from the system clock when no manual override is provided.Component Time EstimationRider pickup time is modeled as double the rider travel distance from the restaurant, capturing the round-trip proximity cost. Three rider proximity buckets are defined: Near (0.5–2 km, mean 1.25 km), Medium (2–5 km, mean 3.5 km), and Far (5–8 km, mean 6.5 km). A uniform random perturbation in [0.9, 1.1] simulates variability in rider availability.Restaurant preparation time is parameterized per food category: pizza (12–18 min), burger (8–12 min), sandwich (5–8 min), and taco (6–10 min), with a ±10% stochastic perturbation.ETA Aggregation FormulaThe final ETA integrates all components as follows:	ETA = max(PickupTime, PrepTime) + DeliveryTime	The max() operator models the practical reality that delivery dispatch occurs only after both the rider arrives at the restaurant and food preparation is complete. Delivery time is computed by the destination-region microservice, either locally if the source and destination belong to the same cluster, or via a REST call to the appropriate remote cluster's /calc_delivery endpoint.Gossip Synchronization protocolFig. 5. Gossip ring synchronization topology between three regional edge nodes.Protocol DesignEach regional node maintains a state object containing two fields: avg_eta (the running weighted average ETA observed by that node) and samples (the total number of ETA computations performed). A background daemon thread executes the gossip loop every five seconds, sending the node's current state to one peer via an HTTP POST to /sync.The gossip topology forms a ring: East synchronizes to West, West to Central, and Central back to East. This ring structure ensures that information originating at any node reaches all other nodes within two gossip intervals under normal operation, providing eventual consistency with low message complexity.Weighted Average MergeWhen a node receives a /sync message, it merges the incoming state with its local state using a sample-count-weighted average:avg_eta_new = (avg_eta_local × n_local + avg_eta_remote × n_remote) / (n_local + n_remote) 	This merge function is commutative and associative, ensuring that the global average converges to the true fleet-wide ETA average regardless of the order in which gossip messages are received. It is also idempotent with respect to repeated merges of the same state, preventing double-counting.Fault ToleranceThe gossip loop wraps all network calls in try-except blocks. If a peer is unreachable, the failure is logged and the loop sleeps for the standard interval before retrying. Because each node maintains its own local state independently, temporary peer failures do not corrupt ETA computation for requests handled by the operational node. The system degrades gracefully: individual clusters continue serving requests in isolation, and global state synchronization resumes automatically once connectivity is restored. Cross-cluster requests will require one extra HTTP round trip to the destination-region node. In a LAN configuration or deploying at the same site, that overhead is in single digits of milliseconds versus round-trip latencies that would normally be seen with cloud-based systems that are centralized and under heavy loads.ETA AccuracyThe ETA equation was designed to predict delivery time based on known delivery times in Mumbai. Under high traffic for example, an intra-cluster delivery of 5 kilometers at a speed of 15 kilometers/hour will result in a delivery leg of 20 minutes. If I were to add 3.5 kilometers in rider proximity (medium) and burgers take 10 minutes on average to prepare, I now have an estimated time of arrival for delivery = max (20,10) + 20 = 40 minutes, which corresponds closely with actual delivery times experienced during peak hours by the largest platforms. Comparatively, under low traffic, that same delivery would have an estimated time of arrival of about 30 minutes.ResultsEdgeSync demonstrates that partitioning a large metropolitan area into geographic edge clusters and deploying localized microservice stacks is a practical and effective strategy for reducing ETA prediction latency and improving fault tolerance. The gossip protocol provides a lightweight coordination mechanism that does not require any centralized broker, eliminating a critical single point of failure.The current implementation models food preparation time and rider proximity stochastically. In a production deployment, these parameters would be replaced with real-time data: rider GPS streams fed into the Rider Distance Service, restaurant order management system state fed into the Preparation Service, and live traffic feeds (from sources such as Google Maps Platform or HERE Traffic) fed into the Traffic Analysis Service.A limitation of the current geographic partitioning is its static coordinate thresholds. Mumbai's traffic patterns shift seasonally (particularly during monsoon) and over the course of the day. Future work will explore dynamic cluster boundary adjustment driven by observed request volumes and traffic sensor density, as well as the addition of a machine learning ETA aggregator within the ETA Engine microservice to replace the current formula-based computation. [3], [4].The gossip ring topology introduces a maximum synchronization lag of two intervals (10 seconds) for information to propagate across all three nodes. For a production system, a fully connected gossip topology or a shorter interval would further reduce this lag.ConclusionEdgeSync is a new distributed edge computing framework that looks to provide real-time estimated time of arrival (ETA) prediction in large urban areas using distributed edge computing by dividing the city of Mumbai into three geographic edge clusters, each deployed with its own separate stack of Fast-API microservices, so EdgeSync can perform localized ETA computations without any reliance on a centralized cloud-based prediction service.The framework handles cross-cluster deliveries by delegating the delivery request to each cluster's REST API and keeping the global ETA state synchronized across the clusters using a gossip-based synchronization process that merges the ETAs from different clusters using a weighted average.EdgeSync provides computational power closer to the variability of demands within each geographic area and extends the functionality of centralized ETAs where 30–40% inaccuracies are reported during peak hours, allowing users of the interactive Streamlit user interface to simulate real-time delivery scenarios across multiple regions and traffic conditions.Future enhancements of EdgeSync will include integration with live rider GPS and traffic APIs, dynamically adjusting the boundaries of each cluster as needed, and implementing a machine learning ETA algorithm on each regional node. The EdgeSync framework provides a replicable model for deployment of distributed regionally aware delivery intelligence in any large urban population.ReferencesA.
