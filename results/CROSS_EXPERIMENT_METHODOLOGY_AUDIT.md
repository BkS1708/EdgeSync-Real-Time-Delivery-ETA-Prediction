## 2. Detailed Methodological Analysis

### 2.1 Workload Generation & Determinism
- **Payload Schema:** Every ETA request contains standard geospatial parameters: `origin: [lat, lon]`, `dest: [lat, lon]`, `departure_time`, `vehicle_type`, and `route_waypoints`.
- **Workload Identity:** Workloads are deterministically generated by `experiments/workloads/generator.py` with fixed random seed `42` and logged with cryptographic SHA-256 hashes (`workload_hash`).
- **Paired Design:** For every request ID (`req_0001` through `req_0100`), exactly the same input coordinates and parameters are evaluated against Centralized, EdgeSync Local, and EdgeSync Remote configurations, ensuring perfect paired-sample comparisons.

### 2.2 Warm-Up Methodology & Data Isolation
- **Warm-Up Isolation:** In `run_full_scalability_experiment.py`, 20 warm-up requests are executed prior to each measurement window. The resulting warm-up data points are tagged (`warmup=True`) and strictly stripped from the measured CSV datasets (`results/scalability/raw/*.csv`), ensuring that JIT compilation, connection establishment, and ASGI routing initialization do not skew steady-state latency metrics.
- **Connection Priming:** In the controlled latency, locality, and network sensitivity experiments, an initial handshake request primes the TCP socket pool prior to latency capture.

### 2.3 Connection Pooling & Socket Reuse
- **HTTP Transport:** All Gen 3 experiments employ persistent HTTP/1.1 keep-alive connection pooling over IPv4 loopback (`127.0.0.1`).
- **Elimination of Ephemeral Port Exhaustion:** By avoiding TCP connection teardown per request, socket allocation latency ($< 0.1\text{ ms}$) is held constant across all architectural conditions.

### 2.4 Timing Mechanism & Measurement Boundaries
- **Clock Source:** All execution timers utilize Python's `time.perf_counter()`, offering sub-microsecond resolution on Windows OS.
- **Decomposition Boundaries:**
  1. `total_latency_ms`: Client-perceived end-to-end latency (dispatch to complete response parsing).
  2. `system_latency_ms`: Middleware routing and dispatch overhead within the FastAPI ASGI pipeline.
  3. `network_latency_ms`: Inter-service HTTP delegation transit time ($T_{\text{client}} - T_{\text{server}}$).
  4. `domain_latency_ms`: Algorithmic ETA computation execution time.

### 2.5 Network Emulation & Calibration
- **Emulation Architecture:** Network delay is injected exclusively on inter-service HTTP delegation paths (e.g., East $\to$ West regional forwarding) via calibrated delay injection.
- **Loopback Calibration:** The network calibration sweep explicitly established baseline loopback overhead:
  - Configured $0\text{ ms} \implies \text{P50} = 1.598\text{ ms}$
  - Configured $5\text{ ms} \implies \text{P50} = 7.232\text{ ms}$
  - Configured $10\text{ ms} \implies \text{P50} = 12.306\text{ ms}$
  - Configured $20\text{ ms} \implies \text{P50} = 22.351\text{ ms}$
  - Configured $50\text{ ms} \implies \text{P50} = 52.425\text{ ms}$
- **Scientific Limitation:** All network delays represent emulated inter-service delegation over local IPv4 loopback, **NOT real-world geographic WAN Internet routing**.

### 2.6 Concurrency & Scalability Harness
- **Worker Pool:** Concurrency is implemented via `concurrent.futures.ThreadPoolExecutor` matching the exact concurrency level $C \in \{1, 2, 4, 8, 16, 32, 64\}$.
- **Throughput Calculation:** Throughput (RPS) is computed as $\text{RPS} = \frac{N_{\text{measured}}}{\Delta t_{\text{wallclock}}}$, where $\Delta t_{\text{wallclock}}$ is the exact span from the dispatch of the first measured request to the receipt of the final response.
- **Resource Instrumentation:** CPU utilization (`psutil.Process().cpu_percent()`) and Resident Set Size (`memory_info().rss`) were sampled asynchronously during benchmark runs.

### 2.7 Fault Injection & Recovery Protocol
- **Fault Types:**
  1. *Peer Process Crash:* Immediate process kill (`SIGKILL`) of remote regional worker during request stream.
  2. *Peer Unavailability:* Port connection refusal / HTTP 503 rejection.
  3. *Network Partition:* Application-level peer blocking in router middleware.
  4. *Packet Loss:* Random probabilistic packet discard in software emulator.
  5. *Node Recovery:* Process restart of crashed node during active workload execution.
- **Fallback Execution:** When remote forwarding fails or times out, EdgeSync automatically routes the request to its local internal ETA estimation engine.

## 3. Methodological Differences Affecting Cross-Experiment Interpretation

1. **Locality Sweep vs Concurrency Matrix:**
   - In the Locality experiment, requests are executed sequentially ($C=1$) to isolate routing decisions from thread contention.
   - In the Scalability experiment, locality is fixed (100% Local vs 100% Remote) while concurrency $C$ varies from 1 to 64.
   - *Interpretation Rule:* Throughput scaling metrics from the scalability experiment cannot be directly extrapolated to arbitrary locality mixtures without accounting for concurrency queue depth.

2. **Loopback Emulation vs Real WAN:**
   - In loopback emulation, TCP resets upon process termination occur in $< 1\text{ ms}$, triggering instantaneous fallback.
   - In physical WAN deployments, peer crashes incur TCP connect timeouts ($500\text{ ms} - 3000\text{ ms}$) unless heartbeat-based failure detectors are active.
   - *Interpretation Rule:* The low fallback latency ($26.57\text{ ms}$) observed in `scenario_1_peer_crash` reflects application-level fallback speed upon fast socket termination, not physical wide-area link timeouts.

3. **In-Memory vs Persistent Storage:**
   - The state synchronization mechanism (`ObservationStore`) runs entirely in memory.
   - State convergence is verified via in-memory set unions and SHA-256 observation hashes.
   - *Interpretation Rule:* Eventual consistency guarantees hold for volatile distributed memory, but durable persistence across total cluster power failure was not benchmarked.
